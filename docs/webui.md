# 웹 UI

[README](../README.md) · [설치](install.md) · [요구 사항·네트워크](requirements.md) · [사용법](usage.md) · [설정·LLM](configuration.md) · [웹 UI](webui.md) · [Windows](windows.md) · [터미널 메뉴](terminal-ui.md) · [개발·검증](development.md)

PC나 서버(Windows·macOS·Linux)에서 실행하고 브라우저로 쓰는 화면입니다. 분석할 서버에 SSH로 접속할 수 있는 컴퓨터면 노트북, 데스크톱, 관리 서버 어디서든 됩니다. 장애 현장에서는 터미널 메뉴를, 평소 분석과 결과 확인은 웹 UI를 쓰면 됩니다.

```text
[웹 UI 컴퓨터: 웹 UI + 브라우저] ──SSH──▶ [분석 서버: analyze-kdump -r] ── crash 리포트 생성 (진행 바 실시간 표시)
          ◀────────────── 리포트 가져오기 ──────────────┘
          └─▶ LLM 분석 (웹 UI 컴퓨터의 API 키 또는 Claude Code·Codex 구독)
```

## 실행

```bash
python webui/kdump-webui.py
```

- **요구 사항:** Python 3.8 이상과 `ssh`. 표준 라이브러리만 써서 따로 설치할 것이 없고, Windows 10/11에는 OpenSSH가 들어 있습니다. 저장소를 받아 그대로 실행합니다.
- **접속:** 실행하면 브라우저가 열리고, 콘솔에 `http://127.0.0.1:8730/?t=<토큰>` 주소가 나옵니다.
  - `127.0.0.1`에서만 듣고, 이 토큰 주소로 들어온 브라우저만 쓸 수 있습니다. 토큰은 실행할 때마다 바뀝니다.
  - 다른 Host 이름이나 다른 사이트에서 온 요청은 거부합니다(DNS 리바인딩, CSRF 방지).
- **옵션:**
  - `--port`(기본 8730), `--data-dir`(기본 `~/.kdump-tools-web`)
  - `--no-browser`, `--no-supervisor`
  - `--service`, `--token-file`, `--show-url`: [서버에서 상시 실행](#서버에서-상시-실행-systemd)
- **다시 시작:** 처음 실행한 프로세스는 콘솔을 맡는 감시 프로세스이고, 실제 서버는 그 아래에서 돕니다. 화면의 **웹 UI 다시 시작**을 누르면 서버만 디스크의 코드로 다시 뜹니다. 이 버튼은 버전·업데이트 화면, 업데이트 직후 안내, 다시 시작 필요 안내에 있습니다.
  - 토큰과 포트가 그대로라 다시 로그인하지 않아도 되고, 페이지도 자동으로 다시 열립니다.
  - 진행 중이거나 대기 중인 작업이 있으면 다시 시작하지 않습니다.
  - `--no-supervisor`로 실행하면 감시 프로세스 없이 한 프로세스로 돌고, 화면에서 다시 시작할 수 없습니다.
- **저장 위치:** 서버 목록, 설정, 가져온 리포트와 분석은 데이터 디렉터리에 저장합니다. API 키와 Claude Code 장기 토큰은 `secrets/`에 두고, 화면과 API 응답에는 내용을 보여 주지 않습니다([API 키와 토큰 저장](#api-키와-토큰-저장)).

### Windows에서 아이콘으로 실행

콘솔을 열지 않고 바탕화면 아이콘으로 실행합니다.
- **아이콘 만들기:** `windows\install-shortcut.cmd`를 한 번 더블클릭하거나 `python webui\kdump-webui.py --install-shortcut`을 실행하면, 바탕화면과 시작 메뉴에 **kdump-analyzer 웹 UI** 아이콘이 생깁니다.
  - `--shortcut-dir <폴더>`로 위치를 정하고, `--remove-shortcut`으로 지웁니다.
- **동작:** `pythonw.exe`로 콘솔 창 없이 서버를 띄우고 브라우저를 엽니다. 이미 실행 중이면 그 서버의 화면을 엽니다.
- **종료:** **버전·업데이트** 화면의 **웹 UI 종료** 버튼을 누릅니다. 진행 중이거나 대기 중인 작업이 있으면 종료하지 않습니다.
- **로그:** 출력은 데이터 폴더의 `webui.log`에 남습니다(1MB가 넘으면 `webui.log.old`로 넘김). 시작에 실패하면 대화 상자로 알립니다. 실행 중인 서버의 주소와 토큰은 `run.json`에 있습니다.
- Python이 설치된 PC가 필요합니다. 저장소 폴더를 옮겼으면 아이콘을 다시 만듭니다. 업데이트(`git pull`)와 다시 시작은 그대로 됩니다.

### 서버에서 상시 실행 (systemd)

새 덤프 자동 분석은 웹 UI가 켜져 있을 때만 동작합니다. 개인 PC 대신 관리용 Linux 서버에서 서비스로 돌리면 밤사이 생긴 덤프도 놓치지 않습니다.

- **서비스 모드(`--service`):** systemd 같은 서비스 관리자 아래에서 실행합니다.
  - 정한 포트(`--port`)에서만 듣고, 감시 프로세스와 브라우저를 띄우지 않습니다.
  - 접속 토큰을 데이터 폴더의 `service-token`(소유자만 읽기)에 두고 계속 씁니다. 위치는 `--token-file`로 바꿉니다. 서비스를 다시 시작해도 접속 주소가 그대로이고, 토큰을 바꾸려면 파일을 지우고 다시 시작합니다.
  - 화면의 **웹 UI 다시 시작**(업데이트 적용)은 종료 코드 75로 끝나고, 서비스의 `Restart=always`가 새 코드로 다시 띄웁니다.
- **접속:** 보안 설계는 같아 `127.0.0.1`에서만 듣습니다. 내 PC에서 SSH 포트 전달로 접속합니다.
  ```bash
  ssh -L 8730:127.0.0.1:8730 <사용자>@<관리 서버>
  ```
  그다음 내 PC 브라우저에서 `--show-url`이 알려 주는 `http://127.0.0.1:8730/?t=<토큰>`을 엽니다. 내 PC 쪽 포트도 8730이어야 합니다(다른 포트는 Host 확인에서 거부).
- **요구 사항:** Python 3.8 이상, `ssh`, `git`(화면에서 업데이트할 때). RHEL 8은 기본 `python3`가 3.6이라 `dnf install python39`로 설치하고, 서비스 파일의 Python 경로를 `/usr/bin/python3.9`로 바꿉니다.

설치 순서 (관리 서버, root):

```bash
# 1) 전용 계정과 저장소 (화면에서 업데이트하려면 이 계정이 저장소에 쓸 수 있어야 합니다)
useradd -r -m -d /var/lib/kdump-webui -s /sbin/nologin kdumpui
git clone https://github.com/621dev/kdump-analyzer.git /opt/kdump-analyzer-webui
chown -R kdumpui: /opt/kdump-analyzer-webui

# 2) 분석 서버에 접속할 SSH 키 (암호 없는 키, 공개 키를 각 분석 서버에 등록)
sudo -u kdumpui mkdir -p -m 700 /var/lib/kdump-webui/.ssh
sudo -u kdumpui ssh-keygen -t ed25519 -N '' -f /var/lib/kdump-webui/.ssh/id_ed25519

# 3) 서비스 등록과 시작
cp /opt/kdump-analyzer-webui/webui/kdump-webui.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now kdump-webui

# 4) 접속 주소 확인
sudo -u kdumpui python3 /opt/kdump-analyzer-webui/webui/kdump-webui.py --show-url --data-dir /var/lib/kdump-webui/data
```

- **SSH 키:** 웹 UI에서 서버를 추가할 때 키 파일은 `/var/lib/kdump-webui/.ssh/id_ed25519`를 씁니다.
  - 서비스에는 ssh-agent가 없어 암호(passphrase)를 건 키는 쓸 수 없습니다.
  - 분석 서버마다 이 키 전용 계정을 만들고 필요한 sudo만 주는 것을 권합니다.
- **관리:** 로그는 `journalctl -u kdump-webui`로 보고, `systemctl stop|start kdump-webui`로 멈추고 시작합니다.
- **키 보관:** Linux에서는 API 키와 Claude Code 장기 토큰을 암호화하지 않고 `secrets/`에 소유자만 읽게 저장합니다. 전용 계정과 `UMask=0077`로 다른 계정이 읽지 못하게 합니다.
- **알림:** 데스크톱 알림은 웹 UI를 열어 둔 브라우저에서만 뜹니다. 화면을 열지 않아도 자동 분석 결과는 분석 기록과 **최근 자동 분석**에 남습니다.

## 화면 구성

### 서버 목록과 서버 화면

- **서버 목록 (왼쪽):** 서버를 추가, 수정, 삭제합니다. 양식 한 장에 다음을 입력합니다.
  - 이름, `user@host`, 포트, SSH 키 파일
  - 원격 analyze-kdump 경로, crash 디렉터리
  - 분석 방식, sudo
- **서버 화면:**
  - **연결 테스트:** 호스트, 원격 analyze-kdump 버전, crash 버전, vmcore 개수를 보여 줍니다.
  - **vmcore 목록:** **리포트** 또는 **리포트 + LLM 분석**을 실행합니다. 기록 칸에는 vmcore마다 만든 리포트와 분석 개수가 보이고, 누르면 최근 결과가 열립니다.
  - **여러 vmcore 한 번에:** 체크박스로 고른 뒤 **리포트**, **리포트 + LLM 분석**, **LLM 분석만(기존 리포트)** 중 하나로 실행합니다. "LLM 분석만"은 crash를 다시 돌리지 않고 vmcore마다 가장 최근 리포트로 분석합니다. 리포트가 없는 vmcore는 건너뜁니다.
- **서버 준비 (서버 화면의 탭):** 서버의 kdump 분석 환경을 점검합니다. 점검만으로는 서버를 바꾸지 않습니다.
  - 점검 항목: kdump 서비스, crashkernel 예약, kdump 동작 준비, crash, 실행 중인 커널의 디버그 커널(vmlinux), 메모리와 swap, 덤프 저장 공간, analyze-kdump
  - 빠진 항목은 골라서 설치합니다(RHEL 계열은 dnf, Ubuntu·Debian은 apt).
  - crashkernel 설정은 재부팅해야 적용되고, 재부팅은 직접 합니다.

### 작업

- **작업 대기열:** 요청한 순서대로 실행합니다.
  - 같은 서버의 crash 작업(리포트 생성, 설치)은 한 번에 하나씩 합니다. 메모리가 작은 서버에서 crash 여러 개가 동시에 돌다 OOM으로 죽지 않게 하기 위해서입니다.
  - LLM 분석은 모든 서버를 통틀어 한 번에 하나씩 합니다.
  - 앞 작업이 LLM 단계로 넘어가면 다음 작업의 리포트 생성이 바로 시작됩니다.
  - 대기 중인 작업은 카드에서 취소합니다.
  - crash 리포트 생성이 설정의 제한 시간(기본 30분)을 넘기면 원격의 crash까지 끝내고 실패로 처리합니다. 멈춘 crash 하나가 그 서버의 대기열을 막지 않게 합니다. 서버 준비와 설치는 2시간으로 제한합니다.
- **작업 카드 (오른쪽 아래):**
  - 표시: crash 리포트 생성 진행 바(`3/12 bt -a`), vmlinux 읽는 중, LLM 분석 단계, 경과 시간, 로그
  - 성공한 카드는 8초 뒤 닫힙니다. 마우스를 올려 두거나 로그를 펼치면 남습니다.
  - 실패한 카드는 직접 닫을 때까지 남습니다.

### 분석 기록과 결과

- **분석 기록 (왼쪽 위):** 모든 서버의 기록을 리포트 단위로 묶어 최신 순으로 보여 줍니다.
  - 표시: 판정 요약, 장애 유형 배지와 판정 근거, panic 문자열, D 상태 태스크 수와 taint 모듈, vmcore, 커널, LLM provider와 모델
  - 필터: 서버, 종류(LLM 분석 있음, 리포트만, 자동 분석만), 장애 유형, 검색
  - 이전 분석 열기, 다시 분석, 삭제. 삭제한 서버의 기록도 볼 수 있습니다.
  - 서버 화면의 "분석 결과" 탭은 같은 목록을 그 서버만 보여 줍니다.
- **판정 한 줄:** 분석 파일에서 다음 순서로 찾습니다. 기본 프롬프트는 LLM에게 보고서 첫 줄을 `판정: <한 문장>`으로 쓰게 합니다.
  1. `판정:` 줄
  2. 요약 표의 판정·근본 원인 행
  3. `추정 근본 원인:` 항목
  4. "근본 원인" 제목 아래 첫 문장
- **분석 결과:** LLM 분석을 제목, 표, 코드를 갖춘 보고서로 보여 줍니다. 원본 리포트로 이동, **보고서로 내보내기**, **삭제**를 할 수 있습니다.
- **리포트 보기:**
  - 맨 위 JSON 요약 상자: 장애 유형, 판정 근거, 패닉 메시지, D 상태 태스크, taint 모듈, 불러온 모듈 심볼, 시스템 값
  - 섹션별 접기·펼치기
  - 검색(해당 섹션만 남기고 강조)
  - 리포트를 LLM으로 (다시) 분석

### 버전·업데이트와 설정

- **버전·업데이트 (왼쪽 위, 상단 버전 배지):**
  - 웹 UI의 현재 버전·커밋을 GitHub 최신 릴리스(또는 브랜치)와 비교하고, 새 커밋 목록과 **업데이트**를 보여 줍니다.
  - 서버마다 설치된 analyze-kdump의 버전, 설치 위치, 설치 원본을 보여 주고 **웹 UI 버전 설치/업그레이드** 또는 **GitHub 최신 설치/업그레이드**를 실행합니다.
  - 예전 위치(`/opt/kdump-tools`)에 설치된 서버는 **새 위치로 옮기기**로 `/opt/kdump-analyzer`로 옮깁니다.
  - **삭제**로 서버의 분석 도구를 지웁니다(프로그램만 또는 전부, 서버 이름을 입력해 확인).
- **설정:**
  - provider와 모델(API 모델 목록 불러오기), API 키 저장, 사내 호환 서버 주소
  - 구독 CLI 경로와 장기 토큰, CLI 상태 확인, 연결 테스트
  - 가리기, 입력 크기, 출력 토큰, 제한 시간, crash 리포트 제한 시간(분)
  - 리포트 보관 기간, 자동 분석 확인 주기

화면을 옮길 때마다 주소 끝에 위치(`#/history`, `#/server/<서버>/results` 등)가 남습니다. 브라우저의 뒤로·앞으로 가기로 화면을 오가고, 새로고침해도 보던 화면이 그대로입니다.

## 원격 분석 방식과 SSH

원격 서버는 세 가지 방식으로 분석합니다.
- **원격 설치본 실행:** 서버에 설치된 analyze-kdump를 실행합니다.
- **무설치 실행:** 스크립트를 원격 임시 디렉터리로 보내 실행한 뒤 지웁니다.
- **자동 선택:** 둘 중 하나를 고릅니다.

SSH 키로 비밀번호 없이 접속할 수 있어야 하고, sudo를 쓰면 원격 서버에 비밀번호 없는 sudo(NOPASSWD)가 필요합니다. 처음 접속하는 서버의 호스트 키는 자동으로 등록합니다(`StrictHostKeyChecking=accept-new`).

### 암호(passphrase)를 건 SSH 키

웹 UI는 SSH를 `BatchMode`로 실행해 암호를 묻지 않습니다. 암호를 건 키는 ssh-agent에 등록해 둡니다. 운영 서버용 키라면 암호를 걸고 ssh-agent를 쓰는 것을 권합니다.

```powershell
# Windows: 관리자 PowerShell에서 ssh-agent 서비스를 켜고 부팅 때 자동 시작
Set-Service ssh-agent -StartupType Automatic
Start-Service ssh-agent
# 일반 PowerShell: 키에 암호를 걸고(이미 걸었으면 생략) ssh-agent에 등록. 이때 한 번만 암호를 입력합니다.
ssh-keygen -p -f C:\Users\me\.ssh\id_ed25519
ssh-add C:\Users\me\.ssh\id_ed25519
```

- 등록하고 나면 서버 설정은 바꾸지 않아도 됩니다. Windows ssh-agent는 키를 Windows 계정으로 보호해 보관하므로 재부팅 뒤에도 다시 등록하지 않아도 되고, 새 덤프 자동 분석처럼 사람이 없을 때 도는 작업도 그대로 동작합니다.
- Windows에서는 Windows OpenSSH(`C:\Windows\System32\OpenSSH`)의 `ssh`·`scp`를 먼저 씁니다. Git Bash에서 웹 UI를 실행해도, Windows ssh-agent를 보지 못하는 Git의 ssh 대신 이것을 씁니다.
- 접속이 `Permission denied (publickey)`로 거부되면 오류 메시지와 작업 로그에 해결 방법을 덧붙입니다.
  - 서버 설정의 키에 암호가 걸려 있는지, ssh-agent에 등록돼 있는지 확인합니다.
  - 공개 키 파일(`<키>.pub`)이 같은 폴더에 있으면 ssh-agent에 등록된 키와 지문으로 맞춰 봅니다.
  - 안내하는 방법: `ssh-add` 명령, ssh-agent 서비스 켜기
- macOS·Linux에서는 웹 UI를 실행할 셸에서 `eval "$(ssh-agent)"`와 `ssh-add <키>`를 먼저 실행합니다. macOS는 키체인에 저장하면 로그인할 때마다 자동으로 등록됩니다.

Windows PC의 Hyper-V 기본 스위치(Default Switch)로 띄운 테스트 VM은 켤 때마다 IP가 바뀔 수 있습니다. 접속 대상을 `tester@<VM 호스트 이름>.mshome.net`처럼 이름으로 넣으면 IP가 바뀌어도 접속됩니다.

### API 키와 토큰 저장

설정에서 입력한 API 키와 Claude Code 장기 토큰은 데이터 폴더의 `secrets/`에 저장합니다.
- **Windows:** DPAPI로 암호화합니다.
  - 그 PC에서 같은 Windows 사용자 계정으로 실행한 웹 UI만 풀 수 있어, 파일이 복사되거나 다른 사용자가 읽어도 키가 드러나지 않습니다.
  - 예전 버전이 평문으로 저장한 키는 웹 UI를 시작할 때 자동으로 암호화합니다.
  - 설정 화면에 "이 Windows 사용자 계정으로 암호화"로 표시합니다.
- **macOS·Linux:** 본인만 읽을 수 있는 파일(권한 600)로 저장합니다.
- 데이터 폴더를 다른 PC나 다른 사용자 계정으로 옮기면 암호화한 키는 풀 수 없습니다. LLM 분석이 "저장된 키를 풀지 못했습니다"로 실패하면 설정에서 키를 다시 입력합니다.

### LLM 분석

LLM 분석은 `webui/kdump_llm.py`에서 합니다. analyze-kdump와 같은 방식(가리기, 섹션 단위 축소, provider 호출, 구독 CLI)을 Python으로 옮겨 Windows에서도 동작하고, 분석 파일 형식도 같습니다.
- Claude Code에는 시스템 프롬프트를 파일(`--system-prompt-file`)로 넘깁니다.
- Windows에서는 npm 실행기(`claude.cmd`) 대신 실제 `claude.exe`를 실행합니다. `.cmd`를 거치면 cmd.exe가 인자를 다시 해석하기 때문입니다.

## 업데이트와 서버 설치

- **업데이트 기준:** 기본은 GitHub의 **최신 릴리스**(태그)입니다.
  - 같은 화면의 "업데이트 설정"에서 **브랜치 최신 커밋**으로 바꾸면 릴리스 전 변경까지 받습니다.
  - 웹 UI가 최신 릴리스보다 앞선 커밋(예: main)이면 `최신보다 앞선 버전`으로 표시하고 업데이트하지 않습니다.
  - 저장소와 브랜치(기본 `621dev/kdump-analyzer`, `main`)도 "업데이트 설정"에서 바꿉니다.
- **웹 UI 업데이트:**
  - 릴리스 기준: 최신 릴리스 태그를 받아 현재 브랜치를 그 태그까지 fast-forward(`git merge --ff-only`)합니다.
  - 브랜치 기준: `git pull --ff-only`를 실행합니다.
  - 조건: git으로 받은 저장소여야 하고, 커밋하지 않은 변경이 없어야 하고, 현재 브랜치가 업데이트 브랜치와 같아야 합니다. 맞지 않으면 업데이트하지 않고 이유를 보여 줍니다.
  - 화면 파일만 바뀌었으면 새로고침으로 적용됩니다. Python 코드가 바뀌었으면 웹 UI를 다시 시작하라고 안내합니다.
- **서버 설치·업그레이드:** 서버 설정의 원격 analyze-kdump 경로(기본 `/opt/kdump-analyzer/bin/analyze-kdump`)로 설치 위치를 정하고 서버에서 `install.sh`를 실행합니다. 설정, 접속 서버 목록, 로그, vmlinux는 install.sh가 그대로 둡니다.
  - **웹 UI 버전:** 웹 UI 저장소의 파일을 SSH로 보냅니다. 서버에 인터넷도 `tar`도 없어도 됩니다(`base64`만 사용).
  - **GitHub 릴리스(또는 최신):** 서버가 GitHub에서 업데이트 기준에 맞는 태그나 브랜치를 직접 받습니다. 서버에 인터넷과 `git`(또는 `curl`과 `tar`)이 필요합니다.
  - 두 방식 모두 root 권한이 필요해 서버 설정에서 sudo를 켜야 합니다(비밀번호 없는 sudo).
- **서버 삭제:** 서버의 분석 도구를 **프로그램만** 또는 **전부** 지웁니다.
  - 확인 창에서 서버 이름을 입력해야 실행합니다.
  - 설치 정보(`.install-info`)나 분석 도구가 있는 디렉터리만 지우고, `/usr`, `/etc` 같은 시스템 디렉터리는 지우지 않습니다.
  - 지운 뒤에도 무설치 실행으로 분석할 수 있고, 웹 UI에 저장된 결과는 그대로입니다.

## 덤프 관리

- **목록 머리글:** 덤프 개수와 합계 크기, 덤프 디렉터리가 있는 디스크의 남은 공간을 보여 줍니다(90% 넘게 쓰면 강조).
- **받기:** 덤프를 웹 UI 데이터 폴더의 `dumps/<서버>/`로 받습니다.
  - Linux는 sudo로 읽어 SSH로 받습니다. root만 읽을 수 있는 `/var/crash`도 받습니다.
  - Windows는 scp로 받습니다.
  - 웹 UI 컴퓨터의 여유 공간(덤프 크기 + 1GB)을 먼저 확인합니다.
  - 작업 카드에 받은 크기가 보이고, 받는 중에도 취소할 수 있습니다. 받다 만 파일은 지웁니다.
- **삭제:** 서버에서 덤프를 지웁니다. 확인 창에서 서버 이름을 입력해야 지웁니다.
  - Linux는 덤프가 든 디렉터리(`<덤프 디렉터리>/<시각>/`)를 `vmcore-dmesg.txt` 등과 함께 지웁니다.
  - Windows는 덤프 파일만 지웁니다.
  - 웹 UI에 저장된 리포트와 분석은 지우지 않습니다.
- **안전장치:**
  - 받기와 삭제는 서버 설정의 덤프 디렉터리 안의 덤프만 다룹니다.
  - 서버에서도 실제 경로(심볼릭 링크 해석)로 다시 확인해, 링크로 밖을 가리키는 파일은 다루지 않습니다.
  - 진행 중이거나 대기 중인 작업이 쓰는 덤프는 지우지 않습니다.

## 새 덤프 자동 분석

- **켜기:** 서버 설정의 **새 덤프 자동 분석**을 **리포트만 만들기** 또는 **리포트 + LLM 분석**으로 둡니다. 웹 UI가 켜져 있는 동안 설정의 **자동 분석 확인 주기**(기본 10분)마다 그 서버의 덤프 목록을 확인합니다.
- **처음 확인:** 그때 있던 덤프를 기준으로 기록만 하고 분석하지 않습니다. 그 뒤로 새로 생긴 덤프만 분석합니다.
  - **자동 분석을 켤 때 리포트가 없는 기존 덤프도 분석**을 켜 두면, 첫 확인 때 웹 UI에 리포트가 없는 기존 덤프를 최근 것부터 최대 10개 분석합니다. 덤프 하나에 몇 분씩 걸려 한꺼번에 돌리지 않습니다. 나머지는 덤프 목록에서 직접 분석합니다.
  - 켤 때 막 쓰이던 덤프(1분 이내)는 기준에서 빼고, 다 써진 뒤 새 덤프로 분석합니다.
- **새 덤프 판단:**
  - Windows `MEMORY.DMP`처럼 같은 이름으로 덮어쓴 덤프도 수정 시각이 바뀌면 새 덤프로 봅니다.
  - 방금 쓰인 덤프(1분 이내)는 다 써질 때까지 다음 확인으로 미룹니다.
  - 같은 덤프를 직접 분석하고 있으면 다시 시작하지 않습니다.
  - 웹 UI가 꺼져 있는 동안 생긴 덤프는 다시 켠 뒤 첫 확인 때 분석합니다.
- **알림:** 자동 작업도 같은 대기열과 작업 카드("자동 · 리포트 생성")로 보입니다. 시작과 끝에 화면 알림을 띄우고, 브라우저 탭을 보고 있지 않으면 데스크톱 알림도 보냅니다. 알림 권한은 자동 분석을 켜고 저장할 때 묻습니다.
- **서버 화면의 자동 분석 표시:**
  - 마우스를 올리면 마지막 확인 시각과 결과(새 덤프 수, 접속 실패 이유)가 보입니다.
  - 누르면 그 서버의 최근 자동 분석으로 갑니다.
  - 옆의 **지금 확인**은 확인 주기를 기다리지 않고 그 서버를 바로 확인합니다.
  - 접속에 실패해도 다음 주기에 다시 확인합니다.
- **기록 유지:** 확인한 덤프 목록은 데이터 폴더의 `auto-seen.json`에 남아 웹 UI를 다시 시작해도 이어집니다. 자동 분석을 끄면 그 서버의 기록을 지우고, 다시 켜면 그때 있는 덤프가 새 기준이 됩니다.
- **자동 태그:** 자동 분석이 만든 리포트는 분석 기록과 "분석 결과" 탭에서 **자동** 태그가 붙습니다. 종류 필터의 **자동 분석만**으로 그것만 봅니다.
- **최근 자동 분석:** 분석 기록 위쪽에서 펼치면, 진행 중·대기 중인 자동 작업과 끝난 자동 작업(최근 10건, 모두 보기 가능)이 보입니다.
  - 끝난 작업은 장애 유형, 실패 이유, 취소 여부와 리포트·분석 열기 버튼을 보여 줍니다. 실패해서 리포트가 없는 작업도 여기서 봅니다.
  - 서버 필터를 따릅니다. 서버 화면의 **자동 분석** 표시를 누르면 그 서버로 걸러서 펼칩니다.
  - 기록은 데이터 폴더의 `auto-log.json`에 최근 200건까지 남습니다. 리포트를 지워도 기록은 남고 "리포트 삭제됨"으로 표시합니다.
  - 1.26.0까지의 자동 분석 리포트에는 자동 표시가 붙지 않습니다.

## 보고서로 내보내기

- 리포트나 LLM 분석을 열고 **보고서로 내보내기**를 누르면, 장애 보고서에 첨부할 HTML 파일 한 장(`kdump-report-<서버>-<시각>.html`)을 내려받습니다. 브라우저에서 열어 PDF로 인쇄할 수 있습니다.
- **들어가는 것:**
  - 머리글: 서버, 덤프, 커널, 파일 이름, 내보낸 시각
  - JSON 요약 상자
  - 그 리포트의 가장 최근 LLM 분석
  - 원본 리포트 전문(끌 수 있음)
- **민감정보 가리기**(기본 켬): LLM에 보낼 때와 같은 규칙으로 호스트명, IPv4, MAC, 이메일을 가립니다. 호스트명은 리포트의 `NODENAME`으로 찾아 LLM 분석과 요약에서도 가립니다. IPv6, 사용자 이름, 파일 경로는 가리지 않습니다.
- 파일은 외부 리소스 없이 혼자 열리고(스타일 포함), 인쇄하기 좋게 늘 밝은 화면으로 만듭니다.

## 리포트 삭제

- **기록 단위로 지우기:** 분석 기록이나 서버의 "분석 결과" 탭에서 **삭제**를 누르면 그 리포트, JSON 요약, 그 리포트로 만든 LLM 분석을 모두 지웁니다. 원본 리포트 없이 분석만 남은 기록은 그 분석들을 지웁니다.
- **열어서 지우기:** 리포트나 분석을 열고 **삭제**를 누릅니다. 분석을 열고 지우면 그 분석만 지우고 원본 리포트는 남깁니다.
- **지우는 범위:** 웹 UI 데이터 폴더(기본 `~/.kdump-tools-web/reports/<서버>/`)의 파일만 지웁니다. 서버의 덤프와, 설치본 실행으로 분석 서버의 `logs`에 남은 리포트는 그대로입니다. 되돌릴 수 없습니다.
- 진행 중이거나 대기 중인 작업(LLM 분석 등)이 쓰는 리포트는 지우지 않습니다. 작업이 끝난 뒤 다시 시도합니다.
- 삭제한 서버의 기록도 분석 기록에서 지울 수 있습니다.

## 리포트 보관 기간

- 설정의 **리포트 보관 기간(일)**을 정하면, 기간이 지난 기록(리포트, JSON 요약, 그 리포트의 LLM 분석)을 한 시간마다 지웁니다. 기본값 0은 지우지 않습니다(0~3650일).
- **기록의 나이:** 리포트와 LLM 분석 중 **가장 최근 파일**의 시각으로 봅니다.
  - 오래된 리포트라도 최근에 다시 분석했으면 남깁니다.
  - 원본 리포트 없이 분석만 남은 기록은 그 분석들의 시각으로 봅니다.
- **정리 시점:** 웹 UI를 켜고 2분 뒤 처음 정리하고, 그 뒤 한 시간마다 정리합니다. 설정의 **지금 정리**는 입력한 기간을 저장하고 바로 정리합니다. 마지막 정리 결과는 설정 화면에 보입니다.
- **규칙:** 리포트 삭제와 같습니다.
  - 웹 UI 데이터 폴더의 파일만 지웁니다. 서버의 덤프와 분석 서버의 `logs`는 그대로입니다.
  - 진행 중이거나 대기 중인 작업이 쓰는 기록은 다음 정리로 미룹니다.
  - 삭제한 서버의 기록도 기간이 지나면 지웁니다.

## 웹 UI에 없는 기능

- crash 셸 직접 입력
- vmcore를 가져와 이 컴퓨터에서 crash로 분석하기 (Windows에서는 crash가 동작하지 않음)
- 구독 CLI 설치와 로그인. 웹 UI 컴퓨터에서 `claude auth login`이나 `codex login`으로 직접 로그인하거나, 설정에 장기 토큰을 붙여 넣습니다.
